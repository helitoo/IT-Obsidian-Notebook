
Trong bài viết này sẽ trình bày 3 loại API sau:

| API           | Ra đời                 | Mức độ trừu tượng | Ý tưởng cốt lõi                                                             |
| ------------- | ---------------------- | ----------------- | --------------------------------------------------------------------------- |
| **RDD**       | API đầu tiên           | Thấp              | Tập hợp phân tán các đối tượng Java/Scala; lập trình viên kiểm soát tối đa. |
| **DataFrame** | Spark 1.3              | Cao               | Xây trên RDD, lấy ý tưởng từ SQL (chiếu cột, nhóm dữ liệu,...).             |
| **Dataset**   | Spark 1.6 (thử nghiệm) | Cao               | Mở rộng DataFrame, thêm ràng buộc kiểu chặt chẽ (type-safe).                |

>[!note]
>Kể từ Spark 2.0, Dataset và DataFrame đã được hợp nhất. Dataframe chỉ là alias của `Dataset[row]`.

# RDD (Resilient Distributed Datasets)

**MapReduce** tận dụng sức mạnh của cụm máy tính, nhưng sau mỗi bước xử lý nó ghi kết quả trung gian ra đĩa (HDFS) và không dùng bộ nhớ phân tán. Với các thuật toán lặp (học máy, đồ thị) hoặc truy vấn tương tác, việc đọc/ghi đĩa liên tục khiến hệ thống **tốn thời gian và chậm**.

**RDD (Resilient Distributed Dataset)** ra đời để giải quyết vấn đề này.

**Vậy RDD là gì?**
- **Ở mức trừu tượng**: RDD là tập hợp các bản ghi được chia thành partition và phân tán tự động trên cluster.
- **Ở mức lập trình**: RDD là một bản mô tả về cách tính ra dữ liệu (nguồn dữ liệu + chuỗi transformation, hay còn gọi là *lineage*).

### Các đặc điểm quan trọng của RDD

- **Chỉ đọc (immutable)**: RDD không bị sửa trực tiếp, thực chất nó là 1 chuỗi thao tác lineage. Muốn thay đổi, ta biến đổi nó thành một RDD mới.
- **Lưu tạm trong bộ nhớ**: RDD có thể lưu tạm kết quả của mình vào đâu đó (do bạn quy định).
- **Chịu lỗi mà không cần nhân bản dữ liệu**: RDD là công thức biến đổi dữ liệu, không phải nơi lưu dữ liệu. Nếu dữ liệu mất đi thì hoàn toàn có thể dựa vào RDD để khôi phục.
- **Biến đổi kết hợp được**: Có thể nối nhiều phép biến đổi để tạo ra RDD mới.

### Cách tạo RDD

Có 3 cách:

#### Đọc từ nguồn dữ liệu bên ngoài

Đây là cách thông dụng nhất. Dữ liệu có thể nằm trong HDFS, HBase, Cassandra, hoặc file thông thường.

```python
lines = spark.sparkContext.textFile("hdfs://...")
```

#### Tạo từ RDD khác

RDD gốc **vẫn nguyên vẹn** và có thể dùng cho các thao tác sau.

```python
errors = lines.filter(lambda ln: ln.startswith("ERROR"))
```

#### Song song hóa một bộ sưu tập tập trung

Biến danh sách có sẵn trong chương trình thành RDD phân tán.

```python
data = [1, 2, 3, 4, 5, 100, 8, 7]

distData = sc.parallelize(data)        # Spark tự chọn số phân mảnh
distData = sc.parallelize(data, 10)    # Chỉ định tạo 10 phân mảnh
```

### Transformation và Action

Các thao tác trên RDD chia làm 2 loại:
- **Transformation (biến đổi)**:
	- Tạo ra RDD mới từ RDD cũ. VD: *`map`, `filter`, `reduceByKey`, `join`,...*.
	- Tính *lazy*: Lưu công thức trước, tính ra kết quả sau.
- **Action (hành động)**:
	- Kích hoạt tính toán thật sự và trả kết quả về chương trình chính (driver).
	- VD: *`count`, `collect`, `take`, `saveAsTextFile`,...*.

**VD**: Đếm số bản ghi theo loại, giữ lại loại xuất hiện hơn 10 lần:
```python
result = (file
    .map(lambda rec: (rec.type, 1))
    .reduceByKey(lambda x, y: x + y)
    .filter(lambda kv: kv[1] > 10))

result.collect()   # Action: lúc này mới thực sự chạy
```

Nhờ tính lazy, Spark thấy được toàn bộ chuỗi biến đổi trước khi chạy, từ đó lập lịch tối ưu và ghi lại được lineage.

### Các thành phần của RDD

**Mục tiêu thiết kế của RDD**: Hỗ trợ nhiều thao tác khác nhau, cho phép người dùng lập trình chúng tùy ý mà không bắt bộ lập lịch phải sửa đổi cho từng loại RDD.

Vì vậy, Spark mô tả mọi RDD bằng cùng 5 thuộc tính, hoặc 5 thành phần:

| Thành phần                              | Vai trò                                                                                                                     |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **Partitions**                          | Danh sách các phân mảnh dữ liệu, mỗi phân mảnh gọi là 1 partition.                                                          |
| **Dependencies**                        | Danh sách các RDD mà RDD này cần để thực hiện (dependency).                                                                 |
| **Compute**                             | Hàm tính toán trên từng partition.                                                                                          |
| **Partitioner**<br>(*tùy chọn*)         | Hàm quyết định một bản ghi (key, value) thuộc partition nào dựa trên key. Nó chỉ áp dụng cho Pair RDD (RDD dạng key-value). |
| **Preferred locations**<br>(*tùy chọn*) | Vị trí nguồn dữ liệu ưu tiên để xử lý trước.                                                                                |

### Khả năng chịu lỗi bằng lineage

Mỗi RDD lưu lại **thông tin xuất xứ**: nó sinh ra từ RDD nào, bằng phép biến đổi nào. Nếu một phân mảnh bị mất (máy hỏng), Spark chỉ cần **chạy lại chuỗi biến đổi cho đúng phân mảnh đó**, bắt đầu từ dữ liệu đáng tin cậy.

**VD**:
```python
messages = (spark.sparkContext.textFile("hdfs://...")
    .filter(lambda ln: ln.startswith("ERROR"))
    .map(lambda err: err.split("\t")[2]))
```

Lineage của `messages` là: `HadoopRDD` → `FilteredRDD` → `MappedRDD`. Mất một phân mảnh của `messages` thì Spark đọc lại đúng khối HDFS tương ứng, lọc và map lại, không cần tính lại toàn bộ.

**Ưu điểm**: Không phải nhân bản dữ liệu nên tiết kiệm bộ nhớ và băng thông.

**Hạn chế**: với RDD có chuỗi xuất xứ rất dài, việc phục hồi có thể tốn thời gian --> dùng *checkpoint* (lưu RDD xuống bộ nhớ bền vững để cắt ngắn lineage). Checkpoint có thể do:
- Người dùng chủ động gọi, HOẶC
- Hệ thống tự kiểm soát, HOẶC
- Các cơ chế thông minh hơn (VD xét khối lượng công việc của từng RDD)

#### Lưu trữ tạm (caching) và persist

Mặc định RDD được tính lại mỗi khi có action. Nếu một RDD sẽ **dùng lại nhiều lần**, ta nên yêu cầu Spark giữ nó lại.

```python
rdd.persist()      # Lưu RDD với cấp độ chỉ định
rdd.cache()        # Viết tắt của persist(MEMORY_ONLY)
rdd.unpersist()    # Xóa khỏi bộ nhớ đệm
```

**Các cấp độ lưu trữ thường gặp**:

| Cấp độ            | Ý nghĩa                                                                            |
| ----------------- | ---------------------------------------------------------------------------------- |
| `MEMORY_ONLY`     | Lưu trong RAM; phân mảnh nào không đủ chỗ sẽ được tính lại khi cần                 |
| `MEMORY_AND_DISK` | Ưu tiên RAM, phần dư đẩy xuống đĩa                                                 |
| `MEMORY_ONLY_SER` | Lưu dạng tuần tự hóa trong RAM: tiết kiệm bộ nhớ hơn nhưng tốn CPU để giải tuần tự |
| `DISK_ONLY`       | Chỉ lưu trên đĩa                                                                   |

Với chiến lược lưu trữ, người dùng quyết định **RDD nào cần tái sử dụng** và **lưu theo cách nào**. Người dùng cũng có thể chỉ định cách chia phân mảnh trên từng máy, rất hữu ích để tối ưu vị trí dữ liệu.

#### Khi bộ nhớ đầy: Thuật toán LRU

Khi có RDD mới cần lưu:
1. Nếu bộ nhớ còn trống thì đưa RDD lên bộ nhớ.
2. Nếu không còn thì **loại bỏ một hay nhiều RDD theo cơ chế LRU** (Least Recently Used, ít được dùng gần đây nhất bị loại trước).

Có thể dùng **độ ưu tiên lưu trữ** để ngăn việc loại bỏ các RDD quan trọng.

### Ví dụ: khai thác nhật ký (log mining)

**Tình huống**: Bạn là 1 kỹ sư vận hành. Hệ thống có một file log rất lớn (vài trăm GB), mỗi dòng như sau:
```sh
ERROR	2026-10-31 09:15	Connection timeout to foo-service
INFO	2026-10-31 09:15	User login ok
ERROR	2026-10-31 09:16	Disk full on bar-node
```

Bạn muốn:
1. Lọc ra các dòng `ERROR`.
2. Lấy phần nội dung lỗi.
3. Truy vấn "có bao nhiêu lỗi nhắc đến `foo`?", "bao nhiêu lỗi nhắc đến `bar`?",...

**Vấn đề**: Nếu mỗi câu hỏi đều đọc lại 300 GB từ đĩa thì rất chậm.

**Ý tưởng của Spark**: Đọc và lọc một lần, giữ phần đã lọc trong RAM, các câu hỏi sau chỉ hỏi trên phần nhỏ đó.

File log được chia thành 3 block, nằm trên 3 máy (worker).

RDD: Định nghĩa công thức
```python
# Lấy log
lines = sc.textFile("hdfs://...")

# Lấy ERROR
errors = lines.filter(lambda ln: ln.startswith("ERROR"))

# Lấy nội dung log
messages = errors.map(lambda e: e.split("\t")[2])

# Tạm lưu trong cache
cachedMsgs = messages.cache()
```

Đến đây **chưa nhân viên nào lật sổ**. Bạn mới chỉ viết ra quy trình và ghi chú: "kết quả cuối cùng nhớ giữ lại". Đây chính là chuyện RDD là công thức mà chúng ta bàn ở trên.

**Truy vấn lần 1**: Đếm lỗi có chữ `foo` (lần đầu, chậm):
```python
cachedMsgs.filter(lambda m: "foo" in m).count()
```

`.count()` là 1 action, nên RDD mới bắt đầu xử lý dữ liệu: Mỗi worker:
1. Đọc dữ liệu của mình từ đĩa.
2. Lọc ra các dòng `ERROR`.
3. Cắt lấy nội dung lỗi.
4. Đưa nội dung lỗi lên RAM (nhờ lệnh `cache()`).
5. Đếm xem có bao nhiêu dòng chứa `foo`, trả kết quả cho driver.

Driver: Tổng hợp kết quả từ 3 worker:
```
Worker 1: "foo" = 120
Worker 2: "foo" = 95
Worker 3: "foo" = 140
Driver  : 120 + 95 + 140 = 355
```

**Truy vấn lần 2**: Đếm lỗi có chữ `bar` (lần sau, nhanh):
```python
cachedMsgs.filter(lambda m: "bar" in m).count()
```

Lần này, dữ liệu đã lưu trên cache nên các worker lấy thẳng từ cache, không đọc từ đĩa cứng nữa.

**Tình huống sự cố: Worker bị sập**?
- Worker không cần làm lại tất cả.
- Worker nào bị sập thì dùng 1 worker khác lấy đúng dữ liệu của worker bị sập và thực hiện lại chuỗi linage mà RDD mô tả.

# Dataset và DataFrame

| Ngôn ngữ | Lớp trừu tượng chính                           |
| -------- | ---------------------------------------------- |
| Scala    | `Dataset[T]` và `DataFrame` (= `Dataset[Row]`) |
| Java     | `Dataset<T>`                                   |
| Python   | `DataFrame`                                    |
| R        | `DataFrame`                                    |

### DataFrame

**Khái niệm**:
- Tập dữ liệu **bất biến**, phân tán, tổ chức thành **các cột có tên**.
- Tương đương khái niệm *Bảng* (Table) trong CSDL quan hệ, *`data.frame`* trong R, *DataFrame* trong Pandas Python,... nhưng có nhiều tối ưu hơn.
- Ràng buộc kiểu **không chặt** như RDD/Dataset.
- API: **Scala, Java, Python, R**.
- Trong Scala/Java: `DataFrame = Dataset[Row]` (Scala) và `Dataset<Row>` (Java).

**Nguồn của DataFrame**:
- Tập tin có cấu trúc: `.csv`, `.json`, `.parquet`,...
- Bảng Hive.
- Cơ sở dữ liệu bên ngoài (MySQL, MongoDB, Cassandra,...).
- RDD / Pandas DataFrame / list / data.frame có sẵn.
- Biến đổi (transformation) từ một DataFrame khác.

### Dataset

**Khái niệm**:
- Tập dữ liệu **bất biến**, phân tán.
- **Kế thừa ưu điểm của RDD**: lập trình hướng đối tượng, hàm lambda mạnh mẽ.
- **Kiểu dữ liệu chặt chẽ** (strong typing) → bắt lỗi ngay lúc biên dịch.
- **Kế thừa ưu điểm của DataFrame**: Tối ưu bằng Catalyst, lưu trữ off-heap (Tungsten), tính trước kế hoạch thực thi tốt nhất.
- API: **chỉ Scala và Java**.

### Spark SQL

**Vấn đề:** SQL phổ biến nhưng không đủ cho dữ liệu lớn; RDD linh hoạt nhưng Spark không tối ưu được cho truy vấn, câu truy vấn viết bằng RDD rất rườm rà --> Spark SQL.

**Spark SQL**:
- Là module của Apache Spark tích hợp xử lý quan hệ với API lập trình hàm của Spark.
- Tích hợp chặt chẽ giữa quan hệ và thủ tục thông qua DataFrame.
- Có trình tối ưu hóa Catalyst, dễ mở rộng: thêm nguồn dữ liệu, quy tắc tối ưu, kiểu dữ liệu.

Spark SQL coi mỗi DataFrame như 1 bảng trong cơ sở dữ liệu quan hệ, cứ thế mà truy vấn thôi.

**VD**:
```python
from pyspark.sql.functions import avg

spark.table("people")
    .groupBy("name")
    .agg(avg("age"))
    .collect()
```

Tương đương:
```sql
SELECT name, avg(age)
FROM people
GROUP BY name
```

# So sánh RDD, DataFrame và Dataset

| Tiêu chí                        | RDD                                                       | DataFrame                                                    | Dataset                                                   |
| ------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------ | --------------------------------------------------------- |
| **Cấp độ API**                  | Thấp, kiểm soát thủ công.                                 | Cao, tối ưu tự động.                                         | Cao, tối ưu tự động.                                      |
| **Định nghĩa**                  | Tập hợp phân tán các đối tượng Java/Scala trên nhiều máy. | Tập hợp phân tán tổ chức theo cột có tên (như bảng quan hệ). | Mở rộng của DataFrame: hỗ trợ type-safe + OOP + Catalyst. |
| **Dữ liệu hỗ trợ**              | Có cấu trúc và phi cấu trúc.                              | Có cấu trúc và bán cấu trúc.                                 | Có cấu trúc và phi cấu trúc.                              |
| **Lược đồ (schema)**            | Người dùng tự định nghĩa thủ công.                        | Spark tự suy ra và quản lý.                                  | Tự suy ra, biểu diễn bảng qua _encoder_.                  |
| **Kiểm tra kiểu lúc biên dịch** | Có.                                                       | **Không** (lỗi cột sai chỉ phát hiện khi chạy).              | Có.                                                       |
| **Công cụ tối ưu**              | Không có; lập trình viên tự tối ưu.                       | Catalyst + Tungsten.                                         | Catalyst + Tungsten.                                      |
| **Tuần tự hóa**                 | Serialization của Java – tốn kém.                         | Nhị phân off-heap, không cần Java serialization.             | Encoder + định dạng nhị phân Tungsten.                    |
| **Gom nhóm, tổng hợp**          | Chậm hơn.                                                 | Nhanh, dễ dùng.                                              | Nhanh, dễ dùng.                                           |
| **Trì hoãn tính toán**          | Có (lazy).                                                | Có (lazy).                                                   | Có (lazy).                                                |
| **Ngôn ngữ**                    | Scala, Java, Python, R.                                   | Scala, Java, Python, R.                                      | Chỉ Scala, Java.                                          |

**Khi nào dùng loại nào?**
- **RDD**:
	- Cần **kiểm soát cấp thấp** các biến đổi/hành động trên dữ liệu.
	- Xử lý dữ liệu **phi cấu trúc** (luồng đa phương tiện, văn bản...).
	- Muốn xử lý theo **cấu trúc lập trình hàm** thay vì biểu thức chuyên biệt.
	- **Không cần áp schema** (không cần truy cập thuộc tính theo tên/cột).
	- Chấp nhận **bỏ qua** lợi ích tối ưu và hiệu suất của DataFrame/Dataset.
- **DataFrame / Dataset**:
	- Muốn API **cấp cao, phong phú** (SQL, hàm đặc biệt, lập trình hàm).
	- Cần biểu thức cao cấp: lọc, ánh xạ, tổng hợp, trung bình, tổng, truy vấn SQL, truy cập cột, lambda trên dữ liệu bán cấu trúc.
	- Muốn tận dụng **Catalyst** và sinh mã hiệu quả của **Tungsten**.
	- Muốn **tiết kiệm bộ nhớ** và thời gian tuần tự hóa/giải mã.
	- Muốn **thống nhất, đơn giản hóa** API trên các thư viện Spark.
	- Cần an toàn kiểu lúc biên dịch → chọn **Dataset** (Scala/Java).

| Ngôn ngữ lập trình | Phù hợp với...                                  |
| ------------------ | ----------------------------------------------- |
| R                  | DataFrame                                       |
| Python             | DataFrame, thêm RDD khi cần kiểm soát nhiều hơn |
| Scala / Java       | Dataset (an toàn kiểu) hoặc DataFrame           |
